#### 개요

홈플러스에서 프로모션 개발·운영을 리딩하던 중 개발팀 축소로 여러 프로모션을 병행해야 했습니다. 반복되는 초기 설정과 기능 구성에 드는 부담을 줄이기 위해 Claude Code Skills 기반의 AI 워크플로우를 구축하고 실제 프로모션 개발에 활용했습니다.

대상은 홈플런 같은 핵심 할인 프로모션과 마이스탬프와 같은 반복적인 참여형 프로모션이었습니다. 프로모션마다 디자인과 보상 조건은 달라졌지만 초기 구조를 만들고 기존 기능을 연결한 뒤 운영 설정을 확인하는 작업은 반복됐습니다. 이 과정을 **반복 작업 선정 → 입력·산출물 정의 → 프로젝트 맥락 연결 → 실행·검토 → 지침 개선**의 흐름으로 정리했습니다.

#### 주요 작업

- 프로모션 요구사항 분석, 개발 일정 및 공수 산정, 히스토리 관리 등 개발 리딩
- Claude Code Skills 기반 AI 워크플로우 구축을 통한 프로모션 반복 개발 작업 자동화

  · zeplin MCP 연동 및 개발 규칙 정의를 통한 초기 구조·라우팅 생성과 공통 기능 구성 자동화

  · API 연동 및 설정값 누락 여부를 점검하고, QA에서 발견한 문제를 Skills에 반영하여 반복 오류 방지

- 룰렛, 퀴즈, 출석체크, 스탬프, 쿠폰 발급 등 참여형 공통 기능 개발 및 개선
- 이벤트 구조 개선 및 공통 컴포넌트 재사용성 향상

## 기존 방식에서 반복되던 문제

프로모션은 여러 팀원이 로테이션으로 담당했습니다. 기획서와 디자인을 확인한 뒤 기존 기능으로 구현할 수 있으면 이전 이벤트 코드를 복사하고, 이미지·쿠폰번호·기간·링크·이벤트코드를 변경했습니다. 신규 기능이 있으면 기술 검토와 협의를 거쳐 기능 개발과 백엔드 API 연동을 추가했습니다.

이전 코드에는 필요한 기능뿐 아니라 이전 프로모션의 설정과 불필요한 코드도 함께 들어 있을 수 있습니다. 담당자가 바뀔 때마다 무엇을 그대로 쓰고 무엇을 변경해야 하는지 다시 파악해야 했습니다.

| 반복 작업                                 | 발생했던 문제                                               |
| ----------------------------------------- | ----------------------------------------------------------- |
| 초기 구조와 라우팅 설정                   | 비슷한 기본 설정을 매번 다시 작성                           |
| 이미지·쿠폰번호·기간·링크·이벤트코드 교체 | 일부 값이 이전 프로모션 정보로 남아 오류 발생               |
| 기존 코드 복사                            | 이전 작업의 오류와 불필요한 코드가 다음 프로모션에도 이어짐 |
| API 연동                                  | 기존 함수를 충분히 확인하지 않아 중복 호출 함수 추가        |

여러 프로모션을 병행하려면 작업자가 기억에 의존해 확인하던 내용을 공통 절차로 정리할 필요가 있었습니다.

## 1. 반복할 작업과 직접 판단할 작업을 구분했습니다

먼저 매번 바뀌는 설정값과 재사용할 수 있는 기능을 구분했습니다. 필요한 기능을 선택해 구성할 수 있도록 프로모션 전체보다 기능 단위로 살펴봤습니다.

| 기능          | 재사용을 검토할 부분                    | 프로모션마다 확인·변경할 부분                |
| ------------- | --------------------------------------- | -------------------------------------------- |
| 기본 화면     | 페이지 진입 구조, 섹션·탭, 팝업·링크    | 제목, 이미지, 화면 구성, 버튼 위치           |
| 룰렛          | 회전 동작과 결과 팝업                   | 칸 수, 보상 구성, 서버 결과와 당첨 칸의 연결 |
| 퀴즈          | 선택·제출·결과 처리 흐름, 기존 API 함수 | 회차별 문제·선택지·이벤트코드                |
| 출석체크      | 출석 이력 조회와 참여 요청              | 대상 월, 보상, 이벤트코드                    |
| 스탬프        | 참여 요청과 이력 갱신                   | 주문 조건, 회차, 보너스·완료 보상            |
| 쿠폰·마일리지 | 기존 발급·조회 API 함수                 | 발급 조건, 코드·번호, 유효기간               |

공통 컴포넌트가 있는 기능은 해당 컴포넌트를 활용하고 이벤트별 화면에 구현된 기능은 기존 흐름을 참고해 요구사항에 맞게 구성했습니다. 룰렛은 공통 컴포넌트를 활용했고, 퀴즈와 스탬프는 이벤트별 화면에 기존 API 함수를 연결하는 방식으로 구성했습니다.

기획서 분석, 신규 기능의 기술 검토와 협의, 운영 설정 확인과 최종 QA는 제가 맡았습니다. AI에는 기본 구조 생성, 선택한 기능 구성, 설정 반영과 구현 후 점검을 맡겼습니다.

## 2. 매번 입력할 정보와 결과물을 정의했습니다

Skills에는 여러 프로모션에서 반복해서 적용할 구조와 규칙을 두고, 실행할 때는 해당 프로모션에 필요한 정보를 전달했습니다.

| 구분                  | 포함한 내용                                                                          |
| --------------------- | ------------------------------------------------------------------------------------ |
| Skills에 정의한 기준  | 기본 디렉터리 구조, 공통 기능 목록, 구현 규칙, API 재사용 기준, 제한 사항            |
| 실행할 때 제공한 정보 | 기획 요구사항, 선택 기능, 제플린 URL, 에셋 저장 경로, API 명세, 프로모션별 운영 설정 |
| AI가 구성할 결과물    | 기본 파일 구조, 라우팅 연결, 선택 기능의 화면과 API 연동 코드                        |

입력 항목은 구현 위치와 연결해서 정리했습니다.

| 입력 정보                    | 반영할 대상                              |
| ---------------------------- | ---------------------------------------- |
| 연도·월·URL 이름·제목        | 이벤트 디렉터리와 라우팅 등록 정보       |
| 선택 기능과 참여 조건        | 필요한 콘텐츠 화면과 참여 처리           |
| 디자인 URL과 에셋 저장 경로  | 디자인 조회, 이미지 다운로드와 화면 구현 |
| API 명세와 이벤트코드        | 기존 함수 검토, 요청·응답 처리           |
| 쿠폰번호·보상 구성           | 발급 요청 또는 응답에 따른 보상 표시     |
| 전체 기간·회차별 기간·종료일 | 참여 제어, 회차 전환, 페이지 접근 설정   |
| 이동 링크와 환경별 값        | 기획전·상품·관련 이벤트 연결             |

Skills를 실행할 때 전달한 정보는 다음과 같이 정리할 수 있습니다.

```text
프로모션: 연도 / 월 / URL 이름 / 제목
선택 기능: 룰렛, 퀴즈
디자인: 제플린 화면 URL / 에셋 저장 경로
API: 명세 / 기능별 이벤트코드
보상: 쿠폰번호 / 보상 구성
기간: 전체 참여 기간 / 회차별 기간 / 페이지 종료일
링크: 이동 대상 / QA·운영 환경별 값
```

여기서 이벤트코드는 백엔드에 어떤 이벤트의 참여를 요청하는지 전달하는 값이고, 쿠폰번호는 보상과 연결되는 값입니다. 화면이 정상적으로 보이더라도 이 값들이 틀리면 다른 프로모션에 참여하거나 잘못된 보상을 표시할 수 있어 별도로 확인했습니다.

## 3. AI가 참고할 프로젝트 구조와 재사용 기준을 연결했습니다

AI가 입력값을 어디에 반영할지 판단할 수 있도록 Skills에 프로젝트 구조와 공통 기능을 정의했습니다. 작업에서 참고하도록 연결한 주요 코드의 위치는 다음과 같습니다.

```text
promotion/
├── router/path.ts       이벤트 기본 정보와 화면 컴포넌트 등록
├── promotion.tsx       URL에 맞는 이벤트 화면 표시
├── common/
│   ├── components/     룰렛·섹션·링크 등 공통 UI
│   ├── fetch/          쿠폰·마일리지·참여 API 함수
│   └── hooks/, utils/  로그인·마케팅·시간 처리
└── event/<연도>/<월>/<이벤트>/
    ├── index.tsx       이벤트 화면 조합
    ├── constant.ts     이미지·코드·기간 등 설정
    ├── ga.ts           마케팅 정보
    ├── page/, style/   콘텐츠 화면과 스타일
    └── fetch/          필요한 경우 추가하는 이벤트별 API 함수
```

선택한 기능과 기존 코드에 맞춰 필요한 파일을 구성하도록 했고, API 함수는 `common/fetch`뿐 아니라 `src/api/httpClient/fetch`에서도 찾아 재사용 여부를 확인하도록 했습니다.

### 공통 기능과 프로모션별 설정을 조합하기

룰렛에는 공통 동작과 프로모션별 설정을 나누는 기준을 적용했습니다. 공통 컴포넌트인 `RouletteV2`는 회전과 결과 팝업을 처리하고 이벤트 화면에서 이미지·칸 수·보상 정보와 API 처리 함수를 전달하는 구조를 활용했습니다.

```text
[기존 공통 룰렛]         +         [이벤트별 설정]
 회전 동작·결과 팝업              이미지·칸 수·보상 구성
                                서버 결과 ↔ 당첨 칸·팝업
                        ↓
                 [새 프로모션의 룰렛]
```

AI가 기존 구현을 먼저 확인하고 공통 기능에 프로모션별 설정을 연결하도록 구성했습니다. 예를 들어 윈터홈플런은 서버에서 받은 쿠폰 정보를 당첨 칸과 팝업으로 변환해 공통 룰렛에 전달합니다. 보상 결과는 서버 응답을 따르고 화면은 그 결과에 맞춰 회전합니다.

이때 새 기획이 기존 컴포넌트의 지원 범위를 벗어나는지도 확인했습니다. 보상 구성이나 참여 방식이 달라지면 추가 구현이 필요하므로 기능 이름이 같다는 이유만으로 설정 변경만 진행하지는 않았습니다.

### API는 요청·응답까지 비교하기

출석체크의 `dailyAttendanceSaveFetch`, 마이스탬프의 `relayParticipate`처럼 기존에 사용하던 함수를 재사용 대상으로 삼았습니다. 새로운 화면을 만들 때도 같은 API를 사용할 수 있다면 기존 함수를 활용하도록 기준을 정했습니다.

다만 이름만으로 재사용 여부를 결정할 수는 없습니다. 실제 코드에는 같은 이름의 참여 이력 조회 함수라도 단일 이벤트코드와 GET을 사용하는 경우 이벤트코드 배열과 POST를 사용하는 경우가 있습니다. 목적과 함께 HTTP 메서드, 요청 파라미터, 응답 타입을 비교해야 하는 이유입니다.

Skills에는 기존 구현을 먼저 확인하는 원칙과 API 재사용 기준, 코드 구성의 제한 사항을 정의했습니다. 당시의 기준과 프로젝트 규칙을 함께 정리하면 다음과 같습니다.

- 기존 공통 컴포넌트와 API 호출 함수를 먼저 확인합니다.
- API 재사용 여부는 메서드·요청값·응답 구조를 함께 비교합니다.
- 선택한 기능에 필요한 코드만 구성하고, 이전 프로모션의 설정과 불필요한 코드를 점검합니다.
- 프로젝트의 alias import 규칙을 따르고, 보관용 `archive` 코드를 직접 import하지 않습니다.

### 디자인 조회와 에셋 다운로드를 작업에 포함하기

제플린 MCP 서버를 연동하고, Skills 지침에 디자인 조회와 필요한 이미지 에셋을 로컬에 다운로드하는 절차를 포함했습니다. 실행할 때는 제플린 URL과 저장 경로를 제공했습니다.

```text
제플린 URL → 디자인 정보 조회 → 필요한 이미지 에셋 다운로드 → 화면 구현
```

공식 MCP도 화면·컴포넌트 조회와 로컬 에셋 다운로드를 별도 도구로 제공합니다. 지침에는 이미지 저장까지 수행하도록 작업을 명시했고, 다운로드 대상은 내보내기 가능한 에셋이어야 했습니다. [Zeplin MCP 공식 구현](https://github.com/zeplin/mcp-server/blob/main/src/index.ts), [에셋 다운로드 안내](https://support.zeplin.io/en/articles/1338605-downloading-assets)

## 4. 생성과 검토를 하나의 흐름으로 구성했습니다

전체 흐름에서 AI와 개발자가 맡은 역할은 다음과 같습니다. 신규 기능이 있으면 기술 검토와 협의를 거쳐 구현 방향을 정하고 기존 기능은 프로젝트 구조와 재사용 기준에 따라 구성했습니다.

![에이전트 작업 플로우](/images/project/ai-promotion-workflow.png)

구현 후 AI에는 API 명세와 디자인 반영 여부, 불필요한 코드와 중복 호출 함수를 점검하도록 했습니다.
이벤트코드·쿠폰번호·기간·링크를 확인하고, QA에서 실제 화면과 기능 동작을 추가로 검증했습니다.

코드 검토와 실행 검증도 구분했습니다. API 호출 코드가 명세와 맞는지 확인하는 것과, 실제 참여·보상 결과가 올바른지 확인하는 것은 별도의 작업입니다. 디자인 반영 역시 구현 코드를 살펴보는 것에 더해 화면과 제공된 디자인을 비교하는 과정이 필요했습니다.

## 5. 발견한 문제를 다음 작업의 점검 기준으로 남겼습니다

QA에서 발견한 문제를 수정하고 이후에도 반복될 수 있는 항목은 Skills 지침에 반영하였으며 이 과정을 통해 새 프로모션을 시작할 때 같은 기준으로 점검할 수 있도록 개선했습니다.

점검 범위는 상수 파일에 한정하지 않았고 설정값이 `constant.ts` 외의 콘텐츠 파일과 API 호출부에도 들어갈 수 있어 실제 사용 위치를 함께 확인했습니다. 페이지 접근 기간과 실제 참여 기간도 구분했습니다. 라우팅에 등록한 종료일 외에 기능별 참여 기간과 회차 설정을 살펴보는 것이 필요했습니다.

검증은 에이전트의 1차 점검과 제가 수행한 최종 검토·QA로 나눴습니다. 에이전트에는 제공한 정보와 구현의 일치 여부를 점검하도록 했고, 운영값이 실제 프로모션에 맞는지 확인하고 기능 동작을 검증했습니다. 같은 항목을 확인하더라도 판단 기준과 책임이 달랐습니다.

### 에이전트: 입력·명세·코드의 일치 여부 점검

에이전트의 점검은 ‘어떤 근거로 확인했는가’를 남길 수 있는 작업으로 구성하는 것이 좋습니다. 실제 활용했던 코드 점검을 수행 방법까지 구체화하면 다음과 같습니다.

| 점검 영역           | 에이전트가 수행할 방법                                                                            | 확인할 수 있는 범위                              |
| ------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 기본 정보·라우팅    | 입력한 연도·월·이름과 `path.ts` 등록 정보, import와 화면 컴포넌트를 대조                          | 등록 누락, URL 구성과 컴포넌트 연결의 불일치     |
| 운영 설정           | 이전 프로모션의 이미지 경로·쿠폰번호·이벤트코드·기간·링크를 새 코드에서 검색하고 제공된 값과 비교 | 이전 값 잔존, 입력값 반영 누락, 환경별 분기 누락 |
| API 연동            | 버튼 처리 함수에서 호출 함수·URL 상수·요청/응답 타입까지 추적해 명세와 대조                       | 메서드·필수 파라미터·자료형과 응답 분기 불일치   |
| API 재사용          | 같은 엔드포인트를 호출하는 기존 함수를 검색하고 요청·응답 구조 비교                               | 재사용 후보와 새 함수가 필요한 차이점            |
| 디자인 반영         | 제플린의 에셋·크기·배치 정보와 이미지 참조, 스타일, 버튼 위치 설정 비교                           | 잘못된 에셋, 누락된 요소, 배치 불일치 후보       |
| 참여 조건·상태 갱신 | 로그인·기간·회차 검사와 응답별 분기를 읽고 성공 후 재조회·상태 변경 경로 추적                     | 필요한 처리의 누락 후보와 코드상 갱신 흐름       |
| 코드 정리           | 선택 기능과 구현을 대조하고 참조 검색·ESLint 검사                                                 | 불필요한 기능, 미사용 코드 후보, 규칙 위반       |

예를 들어 출석체크에서는 `dailyAttendanceSaveFetch`에 전달되는 이벤트코드와 응답 처리를 확인하고 성공 후 이력 조회 함수가 호출되는지 추적할 수 있습니다. 마이스탬프는 참여 성공 후 `refreshFetch` 호출과 상태 전달 경로를 확인할 수 있습니다. 이 점검은 갱신 코드의 존재와 연결을 확인하는 것이며 실제 화면에 올바른 값이 표시되는지는 실행 검증으로 이어져야 합니다.

운영 설정도 마찬가지입니다. 에이전트는 제공된 쿠폰번호가 코드에 정확히 반영되었는지 확인할 수 있지만 제공된 번호 자체가 이번 프로모션의 올바른 번호인지는 운영 정보와 대조해야 합니다.

에이전트의 점검 결과에는 확인한 내용과 방법, 발견한 문제, 미확인 항목을 남기도록 한다. 결과를 검토해 수정할 부분과 추가 QA가 필요한 범위를 판단할 수 있습니다.

```text
[점검 결과 형식 예시]
API: 명세의 필수 파라미터와 호출부를 대조 / 실제 서버 요청은 미실행
디자인: 지정한 모바일 화면 폭의 초기 화면 비교 / 결과 팝업은 미확인
코드: 이전 이벤트 이미지 경로 발견 / 해당 파일·위치와 변경안 제시
검사: 실행 명령, 대상 범위와 결과 기록
개발자 확인: 운영 쿠폰번호와 실제 지급 결과
```

### 개발자: 운영 정보의 정확성과 실제 사용자 동작 검증

기획·운영 정보와 에이전트의 점검 결과를 확인하고 QA에서 실제 참여 흐름을 검증했습니다. 에이전트가 발견한 문제 후보의 수정 여부와 최종 배포 가능 여부도 직접 판단했습니다.

| 검증 영역      | 제가 최종 확인할 내용                                                                          |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 운영 설정      | 쿠폰번호·이벤트코드·기간·링크가 이번 프로모션의 확정 정보와 맞는지, QA·운영 값이 올바른지      |
| 화면과 디자인  | 실제 화면의 이미지 비율, 버튼 위치·클릭 영역, 팝업과 모바일 환경에서의 사용성                  |
| API·보상       | 실제 요청과 응답이 의도한 프로모션에 연결되는지, 쿠폰·마일리지 지급 결과가 맞는지              |
| 참여 조건·기간 | 비로그인·앱 전용·중복 참여·마감·회차 전환 등 재현한 시나리오에서 동작이 맞는지                 |
| 참여 후 화면   | 출석 횟수·누적 마일리지·스탬프가 갱신되고, 새로고침 후에도 서버 상태와 일치하는지              |
| 수정·배포 판단 | 에이전트의 수정 제안이 타당한지, 재사용 범위와 영향 범위가 적절한지, 남은 미확인 항목이 있는지 |

출석체크와 마이스탬프에서는 성공 메시지뿐 아니라 참여 후 갱신된 화면 상태도 확인했습니다. 점검 과정에서 반복 가능한 문제를 발견하면 수정에 그치지 않고 Skills의 확인 항목에 반영했습니다.

브라우저 도구와 QA 계정이 준비되면 에이전트도 화면 이동·버튼 조작·요청 기록 확인·스크린샷 비교를 수행할 수 있습니다. 이 경우 개발자는 에이전트가 남긴 실행 근거를 검토하고, 운영 정보와 실제 지급 결과, 추가 확인이 필요한 예외 상황에 집중할 수 있습니다. 자동 실행 여부와 확인 범위는 점검 결과에 명시하도록 하는 것이 좋습니다.

## 적용 후 달라진 점

여러 프로모션에 이 흐름을 적용하면서 설정값 누락 감소, 반복 수정 작업 간소화 등 개발 인력이 줄어든 상황에서도 여러 프로모션을 병행하는 데 드는 부담을 완화할 수 있었습니다.

| 이전 방식                                      | 워크플로우 적용 후                                        |
| ---------------------------------------------- | --------------------------------------------------------- |
| 이전 이벤트 전체를 복사하고 수정 지점을 찾아감 | 프로모션별 정보와 필요한 기능을 입력해 구조와 기능을 구성 |
| 작업자마다 확인 범위가 달라짐                  | Skills의 공통 기준과 구현 후 점검 절차를 활용             |
| 기존 기능과 API를 매번 새롭게 파악             | 참고할 코드와 재사용 기준을 지침으로 제공                 |
| QA 수정이 개별 이벤트에 머무름                 | 반복 가능한 문제를 다음 작업의 지침에 반영                |

제가 맡은 핵심 역할은 자동화할 작업과 직접 판단할 작업을 구분하고, AI가 참고할 구조·규칙·검토 기준을 정하는 일이었습니다. 기획 해석과 신규 기능의 구현 방향을 결정하고, 운영 설정과 실제 동작을 검증하는 역할도 계속 수행했습니다.
